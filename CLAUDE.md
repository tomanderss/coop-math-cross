# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

**Rechenkreuz**-PWA (Kreuzworträtsel aus Rechenaufgaben). Vanilla JS + Vue 3 via ESM — **no bundler, no transpiler, no TypeScript**. Deployed via GitHub Pages; also native iOS/Android via Capacitor (unchanged web app wrapped with `scripts/cap-copy-www.js` → `www/`).

**Spielprinzip:** Auf einem logischen Raster liegen waagerechte und senkrechte
Gleichungen (`a op b = c`, in den höchsten Stufen auch `a op b op c = d` mit Punkt
vor Strich). Sie kreuzen sich wie ein Kreuzworträtsel — ein Feld gehört zu
höchstens EINER waagerechten und EINER senkrechten Gleichung und ist dabei NICHT
mit ihr verkettet. Ein Teil der Zahlen ist vorgegeben, der Rest liegt im
**Vorrat** und wird per Drag & Drop eingesetzt. Der Vorrat enthält EXAKT die
fehlenden Zahlen.

**Unverhandelbare Regeln:** nur ganze Zahlen, jede Division geht auf; jedes
Ergebnis ist positiv — ein Zwischenstand der Plus/Minus-Kette darf dagegen
negativ werden (`4 − 42 + 67 = 29`). Jedes Rätsel hat GENAU EINE Lösung
und ist rein deduktiv — ohne Raten — erreichbar. Ein **Fehler** entsteht NUR,
wenn ein Zug eine Rechnung vollständig macht, die dann nicht aufgeht (das ist
geraten); eine Zahl an der falschen Stelle, bei der alle vollen Rechnungen weiter
stimmen, ist kein Fehler und fällt erst am Ende auf (Steine bleiben übrig).

Das Firebase-Projekt wird mit der Schwester-App *Coop Number Sums* geteilt: die
ANMELDUNG (E-Mail/Passwort, uid) ist dieselbe, die DATEN sind es nicht — alle
Lese-/Schreibzugriffe laufen über `scopedPath()` in `js/firebase.js` unter dem
Wurzelknoten `mc/`. `database.rules.json` enthält deshalb BEIDE Regelbäume und
muss als Ganzes in der Firebase Console veröffentlicht werden.

## Architecture

| File | Role |
|---|---|
| `js/config.js` | Static config only: difficulties, colors, `DEFAULT_SETTINGS`. No logic. Jede Stufe hat ein festes LOGISCHES Raster (`dim`), eine Ziel-Gleichungszahl (`eqTarget`), die erlaubten Rechenarten (`ops`), den Zahlenraum (`maxOperand`/`maxResult`), den Anteil Dreier-Terme (`ternaryChance`), die höchste erlaubte Deduktionsstufe (`maxTier`) und den Ziel-Lückenanteil (`blankRatio`). `genOptionsFor(id, {bigNumbers})` übersetzt das in Generator-Optionen — „Große Zahlen" hebt nur den Zahlenraum an (`BIG_OPERAND_MULT`/`BIG_RESULT_MULT`) und ist für ALLE Stufen erlaubt. Difficulties tragen zusätzlich die UI-Metadaten `accent`/`accentD`/`heat` für die Slider-Auswahl. **Die Leiter wurde einmalig eine Stufe Richtung „leichter" gerückt** (Nutzerwunsch: unten zu leicht, oben fehlte eine Herausforderung): jede Stufe bekam die SPIEL-Parameter der bis dahin nächst-schwereren (Leicht→Sehr Leicht, …, R.I.P.→Bismillah), die alte leichteste Konfiguration fiel weg und R.I.P. ist neu (10×8, eqTarget 40, maxOperand 32, ternaryChance 0.35, genBudget 120 — per Spike gemessen: 1,8 s Median / 5,2 s max off-thread, 46 Steine, 32 Gleichungen; 10×9 wurde verworfen, dort stieg die Generierung auf bis zu 73 s). Name/Symbol/`accent`/`heat` bleiben beim RANG, nur die Spiel-Parameter wandern. Die Statistik gehört zum RÄTSEL, nicht zum Namen, und wandert deshalb mit: `shiftDifficultyStats(byDifficulty, ids)` (storage.js, rein/unit-getestet) gibt jeder Stufe die Werte ihres bisherigen Nachbarn rechts, die neue Spitze startet leer, unbekannte Alt-Ids bleiben unangetastet. `runDifficultyShift()` (app.js) führt das einmalig aus, idempotent über das cloud-syncte Settings-Flag `diffShiftDone` — und läuft VOR `runEndlessBackfill()`: der Backfill rekonstruiert seine Einträge bereits mit den heutigen Leiter-Ids, andersherum versetzte die Verschiebung ihn ein zweites Mal (E2E endless.spec.js fängt genau das ab). **Nicht mitgezogen wird die globale Bestenliste** (`/leaderboard/{difficulty}/{uid}`): ein Client darf nur seinen eigenen Eintrag schreiben, und `publishBestTime` ersetzt nur SCHNELLERE Zeiten — die Listen tragen also weiter Zeiten, die auf den alten Konfigurationen erzielt wurden, und normalisieren sich erst durchs Weiterspielen. Ein sauberer Schnitt bräuchte ein manuelles Leeren des Knotens in der Firebase-Konsole. |
| `js/model.js` | Datenmodell (rein): logisches Raster + Gleichungen (`{dir,r,c,n,ops}`), `eqCells`/`eqIds`, `evalExpr` (Punkt vor Strich, verwirft Kommazahlen/negative Zwischenergebnisse), `equationHolds`, `solutionValues`/`givenValues`/`blankIds`, `validPuzzleShape`. Das ANZEIGE-Raster ist doppelt so fein (2·dim−1): Zahlen auf geraden, Operatoren auf ungeraden Koordinaten. |
| `js/solver.js` | Deduktions-Maschine — ausschließlich ERZWUNGENE Schlüsse, nie Ausprobieren. Stufen: **T1** eine Lücke in einer Gleichung, **T2** mehrere Lücken, aber der Vorrat lässt nur EINE Belegung zu, **T2.5** Kreuzungsfeld (Schnitt der Kandidaten aus waagerechter UND senkrechter Gleichung), **T3** Zählargument über den Vorrat (Wert kommt k-mal vor und passt in genau k Felder). `logicalSolve(puzzle, {maxTier, from})` kann auf einem LAUFENDEN Spielstand aufsetzen (Basis des Tipp-Tutors); `countSolutions` ist die Brute-Force-Gegenprobe für Tests. `enumEquation` bricht bei sehr vielen Belegungen ab und leitet daraus BEWUSST nichts ab (eine abgeschnittene Kandidatenmenge wäre unsicher). |
| `js/generator.js` | Layout → Werte → Lücken → Prüfung, alles seeded (`mulberry32`). `buildLayout` lässt Gleichungen kreuzworträtsel-artig wachsen (mehrere Anläufe; `holeRatio` sperrt vorab Felder = tote Zellen, `wanderChance` erzeugt Ausläufer statt Blöcke); `assignValues` belegt per **MRV-Backtracking** („fail first": immer die Gleichung mit den wenigsten offenen Feldern zuerst — vollständig durch Kreuzungen festgelegte Gleichungen werden dadurch SOFORT geprüft, ohne das lief die Suche in Sackgassen); `carveBlanks` deckt gierig Felder auf und behält eine Lücke nur, solange `logicalSolve` das Rätsel weiterhin ratefrei durchlöst. Deckel `blankRatio`, sonst wäre praktisch alles Lücke. |
| `js/board.js` | Brett-Logik zwischen Modell und UI (rein, unit-getestet): `buildDisplay` (Anzeige-Raster), Vorrat (`buildTray`/`takeFromTray`/`returnToTray` — ein benutzter Stein behält seinen Platz im Array, die UI rendert ihn nicht), `currentValues`, `placementBreaksEquation` (die Fehler-Regel), `solvedEquationSet`, `isBoardSolved`, `progressOf`, **`normalizePuzzle`**. **`trayMatchesBoard`** (rein, unit-getestet) prüft in O(n), ob die OFFENEN Steine exakt die noch fehlenden Zahlen sind — die billige Wache vor `reconcileTray`, das alle ids neu vergibt und deshalb NUR im Schadensfall laufen darf (sonst setzt jeder Zug Auswahl und Vorrats-Rendering zurück). In app.js läuft `healTrayIfDrifted()` damit nach JEDEM `applyChanges`: läuft etwas auseinander, wird der Vorrat aus dem Brett neu abgeleitet — eine Abweichung kann sich nie mehr aufsummieren. **Konfliktauflösung bei GLEICHZEITIGEN Zügen auf dasselbe Feld** (`winsCell` in coop.js, rein/unit-getestet): beide Spieler wenden ihren eigenen Zug sofort an und erfahren erst danach vom fremden — ohne Regel endet jeder beim Zug des ANDEREN und die Bretter laufen auseinander. Der Firebase-**push-Schlüssel** gibt jedem Zug eine Reihenfolge, die BEIDE Seiten identisch lesen (das Schlüssel-Alphabet sortiert lexikografisch = chronologisch); pro Feld gewinnt der spätere Schlüssel („last writer wins"). `Coop.nextEventKey()` RESERVIERT den Schlüssel schon beim Ausführen des Zuges (Firebase erzeugt push-Schlüssel lokal, ohne Server-Antwort; `pushKeyLike` baut das Format nach, wenn keine Verbindung dahintersteht), `send(msg, key)`/`sendTeamEvent(team, msg, key)` schreiben dann genau dorthin — ein GEPUFFERTER Zug (Outbox bei Roster-Lücke, jetzt `{msg, key}`) behält damit seinen Platz und überholt beim Flush keine wirklich späteren Züge. app.js führt dazu das NICHT-reaktive Raster `cellVersion` (`resetCellVersions`/`cellVersionAt`/`stampCellVersions`; es wird nie gerendert, es entscheidet nur), stempelt die TATSÄCHLICH geänderten Felder (`undoSteps`, nicht jede eingereichte Zelle) und filtert eingehende MOVE-Zellen über `Coop.winsCell`. Eine nur TEILWEISE angewandte fremde Nachricht (ein Feld gewinnt, eins verliert) konvergiert über `healTrayIfDrifted` — beide Seiten leiten den Vorrat aus dem Brett ab. Ein Ereignis OHNE Schlüssel darf ein unbeschriebenes Feld weiterhin füllen (sonst verwirft der Filter interne/alte Aufrufe). E2E in coop-robust.spec.js. Zweite Hälfte desselben Fehlers: `srcIsStale(src)` in app.js lehnt einen VERALTETEN Zug ab. Zwischen dem Aufnehmen eines Steins und dem Ablegen kann im Mehrspieler-Modus ein Partner denselben Stein nehmen oder das Herkunftsfeld überschreiben; abgelegt schrieb der Stein dann einen Wert aufs Brett, der dort nicht mehr herkam (`takeFromTray` fand nichts, das spätere `returnToTray` legte einen NEUEN an) — gemeldet als „der Tausch klappt nicht und dann verdoppelt sich eine Zahl". `dropOn`/`dropOnTray` prüfen deshalb gegen den AKTUELLEN Stand, und eine fremde Änderung, die die eigene Auswahl entwertet, lässt sie sichtbar fallen. E2E in coop-robust.spec.js. `normalizePuzzle` macht ein Rätsel wieder DICHT, das durch die Firebase-RTDB gereist ist: `slots` ist ein 2D-Raster mit `null` für jede tote Zelle (die Löcher des Kreuzworts), die RTDB speichert keine `null`-Werte — Zeilen kommen als Objekt mit numerischen Schlüsseln zurück, eine komplett tote Zeile fehlt ganz. `buildDisplay` greift mit `slots[r][c]` zu und warf dann einen TypeError (Vue bricht den Brett-Teilbaum ab = Blackscreen); `validPuzzleShape` verwarf solche Rätsel zudem im Coop-INIT-Guard. Rein/idempotent, unit-getestet. Läuft in `storage.js` (`healSnapshot` in `loadActiveGame`/`-Coop`/`-Endless`/`loadSaves`, `snapshotSolved`/`snapshotProgress`) UND in app.js (`loadPuzzleIntoState`, `validPuzzleShape`). **Jedes neue null-lastige Raster, das über die RTDB geht, MUSS denselben Weg nehmen** (vgl. `normalizeGrid` in coop.js für `placed`/`markedBy`). |
| `js/hinttutor.js` | Nur noch Bausteine für den TRAININGSmodus (die Hinweis-Funktion selbst ist entfernt, s.u.): `nextForcedStep(puzzle, placed, restTray)` sucht über den Solver den nächsten erzwungenen Schritt, `equationText` rendert eine Gleichung mit `□`/`?`. Der Härtetest spielt komplette Rätsel Schritt für Schritt durch (0 Sackgassen erlaubt). |
| `js/training.js` | Trainingsmodus: `nextTrainingStep` liefert nur Schritte der einfachsten Stufe (T1) mit Erklärtext; app.js setzt sie über `applyTrainingStep`. |
| `js/genworker.js` | ES-module Web Worker that runs `generatePuzzle()` off the main thread via **`generateAsync(opts)`** Promise generation (correlated by `reqId`). Used **on-demand** by Solo `newGame` (loading overlay) and Coop-host/Race/Team (ready-lobby loading bar). Falls back to synchronous generation if the worker is unavailable. **No background prefetch** — puzzles are generated only when a round starts (the old startup-time pre-generation of all difficulties was removed; it bogged down slower devices). |

**Ziehen (Drag & Drop):** Der gezogene Stein schwebt um `DRAG_LIFT` ÜBER dem Finger — sonst verdeckt die Hand genau die Zahl, die man schiebt — und wird IMMER dort abgelegt, wo er ANGEZEIGT wird (Anzeige und Trefferpunkt sind dasselbe, `dropPoint()` ist die einzige Quelle für beides). Dazu die Einstellung **`dragScale`** (Darstellung ▸ Reichweite beim Ziehen, 1–4, Default 1 = unverändert): der Stein folgt der Fingerbewegung ab dem Aufnahmepunkt (`dragOrigin`) um diesen Faktor VERSTÄRKT, damit man den oberen Brettrand erreicht, ohne den Finger über den ganzen Bildschirm zu ziehen; das Ergebnis wird ins Fenster geklemmt. `dragOrigin` wird in `onDragEnd` erst NACH `dropPoint(e)` geleert — sonst fiele die Verstärkung genau beim Loslassen weg und der Stein landete unter dem Finger statt dort, wo er zu sehen war. **Brett-Darstellung (Konvention):** Das Brett ist ein ECHTES zusammenhängendes Raster wie beim Sudoku — `gap: 0`, keine losen Kästchen. Jede belegte Zelle (`.cell`, `.opcell`) trägt ihre 1-px-Rasterlinie als AUSSEN liegenden `box-shadow`; benachbarte Zellen legen die Linien exakt übereinander (gleich dick innen wie außen, kein Layout-Einfluss). Zustands-Ringe laufen deshalb NIE direkt über `box-shadow`, sondern über die Variable `--ring`, die in die gemeinsame Deklaration eingesetzt wird — eine `box-shadow`-Regel würde die Rasterlinie überschreiben; Keyframes, die `box-shadow` animieren (`hintGlow`/`trainingPulse`/`resolvePulse`/`hintGroupPulse`), führen die Rasterlinie in JEDEM Keyframe mit. Passend dazu beginnt der Zug erst nach `DRAG_SLOP` px echter Bewegung (`dragArmed` in `onDragMove`), was zugleich das Aufblitzen des Ziehschattens beim Scrollen verhindert.

**Solver tiers** (siehe `js/solver.js`; `maxTier` je Schwierigkeit in config.js):
- **T1** direkt: eine Gleichung hat genau EINE Lücke
- **T2** Kombination: mehrere Lücken, aber der Vorrat lässt nur eine Belegung zu
- **T2.5** Kreuzung: Schnitt der Kandidaten aus waagerechter + senkrechter Gleichung
- **T3** Vorrats-Zählargument (Wert k-mal im Vorrat, passt in genau k Felder)

Alle Stufen sind logisch zwingend und einem Menschen erklärbar. Es gibt KEINE
Hypothesen-Stufe — was der Solver nicht erzwingt, wird verworfen.

**Keine Hinweis-Funktion:** Der Tipp im Spiel ist ENTFERNT (Nutzerwunsch) — samt Knopfleiste unter dem Vorrat, Tipp-Tutor-Karte, `buildHintTutorial` und den `tutor.*`/`hint.*`-Texten. `nextForcedStep`/`equationText` in `js/hinttutor.js` bleiben, weil der TRAININGSmodus sie braucht; der Härtetest „jedes Rätsel löst sich allein aus erzwungenen Schritten" läuft jetzt darüber. **Restlos entfernt sind auch die Spuren**: `hintsUsed`/`hintsLeft`/`HINTS`/`ENDLESS_CFG.startHints` gibt es nicht mehr (Spielstand, Statistik `stats.hintsUsed`/`coopHintsUsed`, Coop-INIT/STATUS-Payloads, Endlos-Snapshot) — „perfekt" hängt jetzt AUSSCHLIESSLICH an `mistakes === 0`. Empfangene Alt-Felder werden schlicht ignoriert (Abwärtskompatibilität in eine Richtung). Weg sind ebenso der Erfolg `selfMade` („ohne einen einzigen Hinweis", wäre jetzt ein Duplikat von `firstWin`) und `Music.sfxHint()`; der Sound-Schalter `sfxHint` schaltete faktisch nur den Chat-Ton und heißt jetzt `sfxChat` (Migration in `loadSettings`: ein gespeichertes `sfxHint` wird übernommen). Mit dem Sortier-Knopf sind `board.sortTray` und die Desktop-Werkzeugtaste (`settings.desktopToolKey`) weggefallen; der Vorrat sortiert sich in `sortTrayAsc` (app.js) nach jedem Zug selbst.

**Vorrat sortiert sich selbst:** Er ist IMMER aufsteigend sortiert (`sortTrayAsc` nach jeder Änderung und beim Laden) und rückt von selbst auf, weil gelegte Steine gar nicht gerendert werden. Sortiert wird das ARRAY, nicht eine Kopie — die Stein-Objekte behalten ihre `id`, ein aufgenommener Stein also seine Auswahl.

**Game modes**: Solo (mit **Live-Umwandlung zu Coop**: „Mitspieler einladen" im Pausenmenü öffnet einen Raum, `state.soloInvite` in app.js; das Spiel läuft solange als Solo weiter — erst der ERSTE Beitritt wandelt um (`completeSoloConversion`: saveSlot→coop, markedBy→eigene uid, Solo-Slot geräumt, Rundenstand als INIT+START in den Raum → Beitretende landen via Direkteinstieg sofort im Spiel; INIT trägt dafür optional lives/maxLives/mistakes und `running:true` (Runde startet DIREKT beim INIT-Empfang, ohne auf das separate START zu warten — keine hängende Bereit-Lobby möglich; alles rückwärtskompatibel). ## Testing

- Unit: `node:test`, no framework. Import `js/` modules directly.
- E2E: Playwright, Pixel 7 emulation, `de-DE` locale, server on port 8099. Helpers in `test/e2e/helpers.js`. State driven via `window.__cns`.
- CI: `.github/workflows/test.yml` — **zwei parallele Jobs**: `Unit` (kein Browser nötig, ~1 min, schnelles Logik-Signal) und `E2E n/3` (Playwright `--shard`; die Summe der Shards ist die vollständige Suite, `fail-fast: false` damit ein roter Shard die anderen nicht abbricht). Grund: an einem gemessenen Lauf (7:04 gesamt) entfielen **6:21 auf `npm test`** und nur ~40 s auf allen Overhead zusammen — die Suite lässt sich also nicht beschleunigen, nur aufteilen. Wanduhrzeit dadurch ~2:45 statt ~7:16. **Die Playwright-Worker-Zahl bleibt bewusst unverändert**: mehr Worker im selben Job erhöhen die Last je Runner und damit genau die lastbedingten Timeouts (`training.spec.js`), Sharding SENKT sie (weniger Tests je Runner). Läuft auf **PRs** (nicht mehr zusätzlich auf `push: master`: der Nachlauf testete nach dem Squash-Merge denselben Baum, der als PR gerade grün war, und kostete jeden Merge doppelt; wir mergen strikt seriell und nur nach grünem PR-Lauf). **Kostenbewusst geschnitten** — der Juli-Verbrauchsbericht zeigte 4738 Actions-Minuten allein für diesen Workflow (76 % des Kontingents, ~680 Läufe): `concurrency` + `cancel-in-progress` (ein neuer Push bricht den überholten Lauf ab — vorher wurden beide bezahlt, der größte Einzelposten, weil ein PR meist mehrere Korrektur-Pushes bekommt), `cache: 'npm'`, **Playwright-Browser-Cache** (`~/.cache/ms-playwright`, Schlüssel = `hashFiles('package-lock.json')`, bei Treffer nur noch `install-deps` statt ~120 MB Chromium-Download), `timeout-minutes: 20` (ohne Limit lässt GitHub einen hängenden Job 6 h laufen = 360 Minuten für nichts) und `paths-ignore` für reine Text-/Release-Dateien. **`sw.js` gehört NICHT in `paths-ignore`**, obwohl `build.js` es bei jedem Release anfasst: der Unit-Test, der jedes `js/`-Modul in der Asset-Liste erzwingt, darf nie ausfallen (unvollständiger Precache = Nutzer offline ausgesperrt) — Release-PRs fahren deshalb weiterhin einen Lauf. Die Testabdeckung ist unverändert (immer die komplette Suite vor jedem Merge).

## Workflow for every code change

1. **`changes.txt`** — add a short German user-facing bullet (e.g. `Ladeanzeige beim Verbindungsaufbau ergänzt`). Source for in-app release notes.
2. **PR + Auto-Merge** — **always create the PR automatically, without waiting to be asked.** As soon as a change is committed and pushed, create a PR targeting `master`, then call `mcp__github__enable_pr_auto_merge` (SQUASH) **in the same turn immediately after** `create_pull_request`, before CI starts. Never push directly to `master`. (This overrides the default "only open a PR when explicitly asked" behavior — opening the PR + enabling auto-merge is the expected default for every change here.)
3. **Diagnostics/logging** — every new feature or non-trivial flow must add `log()` calls (`js/debuglog.js`) at its key points: start/finish of async or expensive work (with `tookMs` timing where relevant), error paths (`catch` blocks), state transitions, and external I/O (Firebase/storage). Pick a sensible category (`game`/`coop`/`firebase`/`storage`/`sw`/`error`/`env`/`perf`/`app`). This keeps the exported Diagnoseprotokoll useful for debugging issues on users' devices. **Keep it low-frequency** — never log per-frame, per-tap, or inside hot loops/render paths (`log()` writes `localStorage` synchronously and would hurt performance). When touching an existing flow, add the logging it's missing.
4. **Update this file** — if the change affects architecture, conventions, commands, or workflow: update CLAUDE.md to reflect it and include the update in the same PR. Keep entries concise.
5. **Cut a release** — **ALWAYS do this automatically after every PR is merged. NEVER ask first — just do it.** Create a new branch from latest `master` (this dedicated release branch is expected and allowed even when your assigned working branch is a different one — cutting the release needs no separate permission and is never a reason to pause and ask), run `node build.js` (bumps version, writes `js/buildinfo.js`, clears `changes.txt`), commit, open a release PR, and merge it immediately (CI is usually already green on a release-only commit). The version only becomes visible in-app once this step is done.

## Autonomer Arbeitsmodus (Feature-Backlog)

Der Nutzer wirft Features/Bugs **jederzeit und gebündelt** in den Chat — auch während bereits
an etwas gearbeitet wird — und erwartet, dass **komplett autonom, sequenziell und in idealer
Reihenfolge** abgearbeitet wird. Verbindliche Regeln für diesen Modus:

1. **Nichts vergessen — Backlog führen.** Jeden neuen Wunsch **sofort als Task anlegen**
   (`TaskCreate`), auch wenn er erst später drankommt. Der Task-Backlog ist die dauerhafte
   Merkliste; nie einen Wunsch nur „im Kopf" behalten.
2. **Immer den Stand melden.** Bei jeder Nutzer-Nachricht und an Meilensteinen kurz zeigen:
   **✅ durch · 🔄 in Arbeit · ⏭️ als Nächstes** (inkl. Reihenfolge). Der Nutzer soll nie raten
   müssen, was passiert.
3. **Ideale Reihenfolge selbst wählen & umsortieren.** Reihenfolge nach Abhängigkeit/Aufbau
   bestimmen (baut B auf A auf, kommt A zuerst) — Tasks dürfen umgeschoben werden. Kurz begründen.
4. **Parallel zur Pipeline arbeiten.** Während eine CI-Pipeline läuft, **nicht idlen**: schon die
   nächste Aufgabe entwickeln. Dafür einen **git-Worktree** (isolierte Kopie) nutzen, damit der
   offene PR-Branch sauber bleibt; nach dem Merge des laufenden PRs den Zweig zurücksetzen und die
   vorbereitete Arbeit übernehmen (cherry-pick).
5. **Ein PR pro Feature**, jeweils voller Workflow (changes.txt → PR + Auto-Merge → grünes CI →
   Merge → **Release cutten**). Nie mehrere unfertige Features in einem PR mischen.
6. **Nur bei echtem Blocker fragen.** Sonst „nach bestem Wissen & Gewissen" entscheiden, die
   Annahme im PR/Chat protokollieren und weitermachen. Fragen sammeln statt einzeln unterbrechen.
7. **Limit/Reset überbrücken.** Wird ein Nutzungs-/Zeitlimit erreicht, per `ScheduleWakeup`
   (o.ä.) einen Wecker auf den Reset-Zeitpunkt stellen und **automatisch weitermachen** — der
   Nutzer soll nur bei Bedarf reinsprechen müssen.
8. **Abschluss-Zusammenfassung.** Wenn der Backlog leer ist (oder auf Nachfrage): kompakte
   Übersicht aller erledigten Punkte + **offene Fragen/Klärungsbedarf/Wünsche** an den Nutzer.

## Key conventions

- **Offline-First** (`sw.js` + `state.net` + Konflikt-Reconcile): Die PWA ist offline (Flugmodus) voll spielbar. **`sw.js`** liefert die App-Shell **cache-first** mit Navigations-Fallback auf `index.html` (Home-Icon startet offline zuverlässig), alle gleich-origin GET-Assets als **stale-while-revalidate**, Fremd-Origin (Firebase) wird durchgereicht; Precache **einzeln** (`Promise.allSettled`) + **atomarer Swap** (alte Caches erst löschen, wenn der neue die Shell hat) → kein Aussperren nach misslungenem Update. **JEDES neue `js/`-Modul MUSS in die `ASSETS`-Liste** (sonst offline nicht ladbar — passierte mit `session.js`). Cache-Version bumpt `build.js` pro Release. **Manuelle Update-Prüfung**: Klick auf die Version im Hauptmenü → `checkForUpdate()` (app.js) stößt `reg.update()` an; wartet danach ein neuer Worker, bietet ein Dialog den Neustart an (`restartForUpdate` → `SKIP_WAITING`-Message an sw.js → `skipWaiting()` → `safeReload`). Weiterhin KEIN automatischer Laufzeit-Update-Flow — ohne Nutzeraktion übernimmt eine neue Version erst beim nächsten Kaltstart. **`state.net`** (`'online'|'offline'|'reconnecting'`, `initConnectivity()` aus `navigator.onLine`+Events+visibilitychange) → `isOnline()`; netzabhängige Aktionen (Coop/Race/Freunde) offline `disabled` + Guard statt Firebase-Timeout; Home zeigt `.offline-chip`; `onReconnect()` triggert `reconcileSession`+`doSyncNow`. Solo/Training sind komplett lokal. **Versions-Mismatch**: `account.isDivergent()` (rein, unit-getestet) erkennt formale Divergenz (lokal UND Cloud seit `syncedRev` geändert); `reconcile()` löst sie INHALTLICH auf — verlustfreier Auto-Merge (`mergeSnapshots`, s.o.) ⇒ `decision:'merged'` still; NUR bei abweichendem Geld-Saldo (`walletBalanceDiffers`) ⇒ `decision:'conflict'` → app.js `openVersionMismatch`/`resolveVersionMismatch(choice)` zeigt den `.mismatch-modal`, die Wahl betrifft NUR das Guthaben (Rest bleibt gemergt); `account.resolveConflict(choice)` wendet an und sichert die unterlegene Seite als Backup (`saveConflictBackup`, nie still gelöscht), dann `safeReload`. **Grenze:** der Erststart muss einmal online sein (GitHub Pages cached erst dann).
**Zell-Gesten (app.js `handleCellTap`/`onCellDown`…`onCellCancel`):** drei Gesten auf einem Zahl-Feld. **Lange drücken** (`LONG_PRESS_MS` 450) schaltet eine PERSÖNLICHE Farb-Markierung (`state.hl`, Schlüssel `"r-c"`) an/aus — sie hat KEINE Regel-Bedeutung, wird NIE an Mitspieler gesendet, wandert aber im Spielstand mit (`activeSnapshot.hl`). Farbe: `settings.markColor`, als `--markhl` am Brett (`gridStyle`), CSS `.cell.marked`. Der Nachschlag läuft über das gecachte `hlSet`-Computed, nie über `Array.indexOf` je Zelle (Render-Kernregel). **Einmal tippen** wählt einen gelegten Stein aus, die Auswahl BLEIBT stehen, ein Tipp auf einen anderen gelegten Stein tauscht. Das ging vorher nur per Ziehen: der `@click`-Handler feuerte NACH dem Zeiger-Pfad, sah die dort gerade gesetzte Auswahl und hob sie als „Ablegen auf sich selbst" sofort wieder auf. Der Zeiger-Pfad entscheidet jetzt selbst (`onCellUp` → `onDragEnd(e, cell)` → `handleCellTap`), `onCellTap` (Tastatur/Maus-Fallback) steigt über `pointerTapAt` aus, wenn derselbe Tipp schon behandelt wurde. **Dreimal tippen** (`TRIPLE_TAP_MS` 700) schickt den Stein zurück in den Vorrat. Alle neuen Handler MÜSSEN im `setup()`-Rückgabeobjekt von `BoardGrid` stehen — sonst rendert Vue still weiter und wirft nur `onCellDown is not a function` in die Konsole. E2E in mathcross.spec.js; ein Tausch-Test MUSS Felder wählen, deren Rechnungen offen bleiben, sonst ist der Tausch zu Recht ein Fehler. **Jede Geste, mit der man das Spiel bedient, MUSS in der Anleitung (`howto.*`, alle Sprachen) stehen** — sie blieb beim Einbau der Gesten zurück und beschrieb nur noch das Ziehen; der E2E-Test „die Anleitung erklaert jede Bedien-Geste" (home.spec.js) hält das fest.

- **Board-Render-Performance (KERNREGELN):** (0) **Das Brett ist eine EIGENE Child-Komponente `BoardGrid`** (app.js, direkt vor `App`; registriert als `<board-grid>`): Vue trackt Render-Abhängigkeiten pro Komponente — App-Renders (Werkzeug-Umschalter `state.tool`, Sekunden-Tick `state.elapsed`, HUD/Chat/Toasts) rendern die ~200 Zellen NICHT mehr mit (vorher: spürbare Tap-Latenz, „Einkreisen/Löschen reagiert nicht", Züge im falschen Modus). Alle Brett-Helfer (`cellClasses`/`cellStyle`/`gridStyle`/`skinVars`/`skinBoardClasses`/Resolved-Computeds/Pointer-Handler) liegen bewusst auf MODULEBENE (kein Props-Threading); NEUE Brett-Bindings gehören ins BoardGrid-Template, App-fremde Abhängigkeiten (z.B. `state.tool`) dürfen dort NICHT einfließen, sonst rendert jeder Tool-Wechsel wieder alles. `window.__cns.boardRenders()` zählt Brett-Renders — der E2E-Test `perf.spec.js` erzwingt die Isolation (Tool-Wechsel/Tick = 0 Renders, echter Zug > 0). Der **Settings-Persist ist ENTPRELLT** (250-ms-Trailing-Timer + `flushSettingsSave` bei pagehide/hidden), weil `toggleTool` bei jedem Wechsel `settings.confirmTool` schreibt und das synchrone stringify+localStorage sonst im Tap-Pfad lag. Außerdem: JEDE reaktive Änderung rendert das restliche App-Template neu. Deshalb: (1) **Hochfrequente reaktive Writes vermeiden** — der Spieltimer schreibt `state.elapsed` nur beim SEKUNDENwechsel (native 250-ms-Abtastung bleibt; vorher: 4 Voll-Renders/s, deren Kosten mit den Markierungen wachsen → auf älteren Geräten Sekunden Tap-Latenz im Spätspiel; `win()`/`lose()` stempeln die exakte ms-Zeit selbst). (2) **`cellStyle` liefert bei unveränderten Eingaben DIESELBE Objekt-Referenz** (`cellStyleCache`, Reset in `loadPuzzleIntoState`) — sonst setzt Vue alle CSS-Custom-Properties (`--rc-*`/`--markcol`) für jede Zelle bei jedem Render neu (`setProperty` war ein Top-Profil-Posten). (3) **NIE `filter` (drop-shadow) auf ein dauerhaft ANIMIERTES Element** — der Skin-Glow liegt als box-shadow auf dem STATISCHEN `::before` unter dem rotierenden `::after` (Filter auf ~165 animierten Layern sättigte den iOS-Compositor: halb gerenderte Kacheln, hängende Taps); `.board.skin-freeze` (bei Pause) hält die Rotation an, damit der `backdrop-filter`-Blur des Pause-Overlays nicht pro Frame neu blurt. (4) **Kein erzwungenes Layout pro Mutation** — `scheduleScrollLockUpdate` (scrollHeight-Messung via MutationObserver) ist auf 250 ms gedrosselt. (5) Aria-Labels/`pulseEdges` sind gecacht bzw. mit Früh-Ausstieg. Im Brett-Template + `cellClasses` NIE pro Zelle die Gleichungen neu durchsuchen — `solvedEquations`/`solvedCellSet` sind cachende Computeds (rechnen nur bei `state.placed`-Änderung neu), die Render-Helfer `eqSolvedR`/`cellInSolvedEq` sind danach O(1). `.cell` trägt `contain: layout style`. **Der Ziehschatten beim Drag & Drop wird DIREKT im DOM bewegt** (`drag-ghost`, `transform`) — eine reaktive x/y-Position würde bei jeder Zeigerbewegung das ganze App-Template neu rendern.
- All UI strings via `t()` from `js/i18n/index.js` — no hardcoded text.

Sonst driftet `syncedRev` vor die Cloud-`rev` (während einer Partie schreibt der Autosave alle 400 ms und bumpt `DATA_REV`), und der Fremd-Änderungs-Schutz in `syncNow` (`cloudRev !== base`) hält ab dann JEDEN eigenen Upload für einen Fremd-Konflikt und überspringt ihn **permanent** — das laufende Spiel und alle Settings kamen nie in der Cloud an („kein Fortsetzen auf dem Zweitgerät", „Theme nicht übernommen"). Jeder neue Upload-Pfad MUSS diese Regel einhalten.

- **Firebase-Schreibvorgänge dürfen NIE `Infinity`/`NaN` enthalten** — RTDB lehnt sonst den GESAMTEN Schreibvorgang ab (kein Teil-Write). Historisch war das `hintsLeft = Infinity` (Hinweis-Funktion, inzwischen entfernt): ungefiltert im Coop-INIT (Solo→Coop) ODER im `writeSession`-Session-Payload ließ es den kompletten Write scheitern (Symptom: Beitretender bekam nur START, kein INIT → „hängt in der Lobby"; Solo-Cloud-Session synct nie). `sanitizeForFirebase(v)` (rein/unit-getestet, dupliziert in coop.js + account.js) ersetzt nicht-endliche Zahlen rekursiv durch `null` (RTDB verwirft den Key → Empfänger setzt seine Defaults) und läuft in `Coop.send`/`sendTeamEvent`, `writeSession` UND `uploadLocal` (Cloud-Daten-Snapshot — unsaniert scheiterte der GESAMTE Sync, sobald ein Aktivspiel-Slot eine nicht-endliche Zahl trug: mitten in einer Partie kam nie ein Upload durch, Symptom „kein Fortsetzen/veraltete Settings auf dem Zweitgerät"). - **RTDB speichert KEINE `null`-Werte — 2D-Raster kommen löchrig zurück.** Ein Array mit Lücken liefert die RTDB als OBJEKT mit numerischen String-Schlüsseln (`{"3":{"5":"uid"}}`), komplett leere Zeilen fehlen ganz. Genau das ist `markedBy` (wer hat welche Zelle markiert): in einer LAUFENDEN Runde sind fast alle Zellen `null`. `loadPuzzleIntoState` übernahm das Raster roh, im Brett-Render warf dann `state.markedBy[r][c]` für jede fehlende Zeile einen TypeError — **Vue bricht den Brett-Teilbaum ab, `.board` fehlt komplett im DOM: DAS war der wiederholt gemeldete „Blackscreen beim Beitritt"** (belegt durch `Beitritt gerendert` mit `cells:0/w:0/h:0` bei korrekt geladenem Spielstand). Ein Vue-Render-Fehler erzeugt KEIN `window.error`-Event, taucht also nie im Diagnoseprotokoll auf — nur die Render-Messung deckte ihn auf. Ein FRISCHES Brett war nie betroffen (kein `markedBy` → Empfänger legt ein leeres Raster an), deshalb traf es ausschließlich den Beitritt mitten ins Spiel (Solo→Coop-Umwandlung, Nachzügler, laufendes Coop-Endlos-Level). Fix beidseitig: `normalizeGrid(raw, rows, cols, fill)` (rein, coop.js, unit-getestet) macht JEDES empfangene/gespeicherte Raster in `loadPuzzleIntoState` wieder dicht (heilt auch alte Spielstände; loggt einmalig `Loechriges markedBy-Raster geheilt`), und `wireMarkedBy()` (app.js) sendet leere Zellen als `''` statt `null`, damit der Payload gar nicht erst zerfällt. **Jedes neue `null`-lastige Raster, das über die RTDB geht, MUSS denselben Weg nehmen.**

- **iOS-PWA-Schwarzbild-Prävention** (`nudgeRepaint(reason)` in app.js): Standalone-PWAs zeigen nach Kaltstart/Rückkehr aus dem Hintergrund (iOS killt aggressiv, im Log massenhaft `pagehide persisted:false`) oft ein SCHWARZES, nicht neu gezeichnetes WebView. `nudgeRepaint` erzwingt beim `visibilitychange`→visible, beim `pageshow` UND nach dem Coop-**INIT** (`nudgeRepaint('coopInit')` direkt nach `navigate('game')`) ein Neuzeichnen via kurzem **Opacity-Stups** (1→0.999→1 an `.app`) — `opacity` erzeugt (anders als `transform`/`filter`) KEINEN Containing-Block für die `position:fixed`-Vollbild-Hintergründe, ist also sicher. Symptom war „Beitretender sieht nach App-Wechsel alles schwarz". Der INIT-Anstoß kam später dazu: dort baut sich ein KOMPLETT neues Brett auf, OHNE dass eines der beiden Ereignisse davor lag — nach einem Kaltstart über eine Einladung die einzige Stelle mit großem frischem Teilbaum ohne Repaint-Anlass (im Protokoll: Brett geladen, Timer gestartet, Wake Lock aktiv, KEINE Ausnahme — der Zustand war korrekt, nur nicht gezeichnet). **Beitritt mitten ins Spiel**: `startJoinFreeze(countMarked())` im INIT-Handler hält die Skin-Rotation 1,8 s an (`state.joinFreeze` → `.board.skin-freeze`, dieselbe Klasse wie die Pause) und protokolliert EINMAL die tatsächliche Render-Lage (`Beitritt gerendert`: Zellenzahl, Brettgröße, markierte Zellen, Skin). Grund: ein Beitretender bekommt den kompletten bisherigen Spielstand in EINEM Frame — bei einer umgewandelten Solo-Partie Dutzende markierte Zellen mit je einer rotierenden Skin-Ebene, während sie in einer normalen Coop-Runde nach und nach entstehen. Genau diese Konstellation hat WebKit schon einmal zerlegt (s. `js/skins.js`). Das Protokoll macht einen erneuten Schwarzbild-Bericht entscheidbar: Brettgröße 0 = gar nicht aufgebaut, Größe > 0 = aufgebaut und nur nicht gezeichnet. Der Coop-INIT-Handler setzt zudem die Coop-Flags (`active/connected/awaitingStart`) VOR `loadPuzzleIntoState`, damit der Beitretende im Coop-Kontext lädt (`saveSlot='coop'`, nicht `solo`).
